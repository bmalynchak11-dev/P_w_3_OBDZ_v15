# Відповіді на питання

---

## Питання 1. Навмисне порушення двох обмежень у psql та аналіз повідомлень

Для перевірки роботи обмежень виконано підключення до бази через `psql` та навмисно подано некоректні команди вставки.

### 1) Обмеження `ck_grade_points` (діапазон балів від 0 до 100)

**Виконана команда в psql:**
```sql
INSERT INTO grade (id, student_id, points, mark, graded_on) 
VALUES (1, 1, 105, 5, CURRENT_DATE);

**Вивід команди:**
ERROR:  23514: new row for relation "grade" violates check constraint "ck_grade_points"
DETAIL:  Failing row contains (1, 1, 105, 5, 2026-10-16).

**Аналіз частин повідомлення:**
Код помилки (SQLSTATE 23514): стандартний п'ятизначний код помилки PostgreSQL check_violation, що сигналізує про невиконання умови перевірочного обмеження CHECK.

Основний рядок (ERROR: new row for relation "grade" violates check constraint "ck_grade_points"):

Вказує дію та цільову таблицю: спроба додати або оновити новий рядок (new row) у відношенні "grade".

Чітко зазначає тип порушення та назву обмеження: порушено обмеження типу CHECK із назвою "ck_grade_points".

Рядок деталізації (DETAIL: Failing row contains (1, 1, 105, 5, 2026-10-16)):

Демонструє фактичні значення всіх полів рядка, який спричинив помилку.

У стовпець points передано число 105, яке порушує логічну умову points BETWEEN 0 AND 100 (значення виходить за межі верхньої допустимої планки 100).


## 2) Обмеження ck_student_record_book (формат номера залікової книжки)

**Виконана команда в psql:**

INSERT INTO student (id, full_name, birth_date, record_book) 
VALUES (1, 'Шевченко Тарас', '2004-03-09', 'ab123456');

**Отримане повідомлення PostgreSQL:**

ERROR:  23514: new row for relation "student" violates check constraint "ck_student_record_book"
DETAIL:  Failing row contains (1, Шевченко Тарас, 2004-03-09, ab123456).

**Аналіз частин повідомлення:**
Код помилки (SQLSTATE 23514): клас помилок check_violation.

Основний рядок (ERROR: ... violates check constraint "ck_student_record_book"):

Повідомляє, що для сутності "student" не виконана перевірка коректності формату, задана правилом "ck_student_record_book".

Рядок деталізації (DETAIL: Failing row contains (1, Шевченко Тарас, 2004-03-09, ab123456)):

Показує передане значення поля record_book: 'ab123456'.

Регулярний вираз ^[A-Z]{2}[0-9]{6}$ суворо вимагає дві великі літери латинського алфавіту та шість цифр. Оскільки літери введено в нижньому регістрі ('ab'), умова повертає FALSE, і PostgreSQL блокує транзакцію.

## Питання 2. Яку помилку в даних захищає кожне обмеження картки і що сталося б, якби його не було?

pk_student (PRIMARY KEY на student.id):

Що захищає: гарантує сутнісну цілісність — унікальність кожного студента та відсутність невизначених значень (NOT NULL).

Якби не було: у системі з'явилися б дублікати записів або записи з id = NULL, через що було б неможливо однозначно ідентифікувати студента чи пов'язати його з оцінками.

pk_grade (PRIMARY KEY на grade.id):

Що захищає: забезпечує унікальність кожної окремо виставленої оцінки в журналі.

Якби не було: виникали б ситуації багаторазової появи однакових записів оцінювання без можливості точкового оновлення чи видалення конкретного запису.

ck_student_birth (birth_date >= '1950-01-01'):

Що захищає: відсікає аномальні, хибні дати народження (випадково введений рік на кшталт 1824, помилки вводу з клавіатури або збої імпорту).

Якби не було: у реєстрі могли б зберігатися фіктивні дані про студентів, яким понад 100–200 років, що спотворювало б аналітику й звіти.

ck_student_record_book (record_book ~ '^[A-Z]{2}[0-9]{6}$'):

Що захищає: уніфікує формат академічного документа студента, дозволяючи лише 2 великі латинські літери (серію) та 6 цифр (номер).

Якби не було: користувачі могли б вводити довільні рядки, кирилицю, пробіли, скорочення чи символи різної довжини, що завадило б інтеграції з державними реєстрами та ускладнило б валідацію.

ck_grade_points (points BETWEEN 0 AND 100):

Що захищає: гарантує відповідність балів стандартизованій 100-бальній шкалі (від 0 до 100 включно).

Якби не було: через опечатку оператор міг би зберегти від'ємні бали (наприклад, -10) або числа, які виходять за діапазон (наприклад, 1000 або 150), що зламало б підрахунок рейтингів і середнього бала.

ck_grade_mark (mark IN (2, 3, 4, 5)):

Що захищає: обмежує академічну оцінку лише дозволеним переліком значень національної 4-рівневої шкали (незадовільно, задовільно, добре, відмінно). Оскільки стовпець допускає NULL, відсутність оцінки (наприклад, до іспиту) не вважається помилкою.

Якби не було: в базу можна було б записати будь-яке числове значення (0, 1, 12, 99), яке не існує в даній системі оцінювання.

ck_grade_date (graded_on <= CURRENT_DATE):

Що захищає: забороняє виставляти дату оцінки в майбутньому відносно поточної дати сервера.

Якби не було: через збитий годинник на клієнтському ПК або помилку користувача оцінки фіксувалися б "наперед" (наприклад, на рік вперед), порушуючи хронологію академічного журналу.

## Питання 3. Яку помилку зроблено першою під час роботи та як повідомлення допомогло її знайти?

Під час початкового написання обмеження ck_student_record_book рядок регулярного виразу було взято в подвійні лапки замість одинарних:
CONSTRAINT ck_student_record_book CHECK (record_book ~ "^[A-Z]{2}[0-9]{6}$")

Реакція сервера та діагностика:
Під час запуску скрипту PostgreSQL повернув помилку:
ERROR: 42703: column "^[A-Z]{2}[0-9]{6}$" does not exist
LINE 8: ..._record_book CHECK (record_book ~ "^[A-Z]{2}[0-9]{6}$")

Як повідомлення допомогло знайти розв'язання:

Код помилки 42703 (undefined_column) та текст прямо вказали, що PostgreSQL трактує подвійні лапки "" як ідентифікатор стовпця (column identifier), а не як текстовий літерал.

Покажчик ^ у рядку LINE вказав точно на символ ".

Це дозволило одразу згадати стандарт SQL та правила синтаксису PostgreSQL: будь-які строкові літерали й вирази регулярних шаблонів мають записуватися суворо в одинарних лапках ('...'):

CONSTRAINT ck_student_record_book CHECK (record_book ~ '^[A-Z]{2}[0-9]{6}$')
